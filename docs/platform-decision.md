# ADR-001. 플랫폼 선정 — 웹 vs 데스크톱 vs 하이브리드

| 항목 | 내용 |
| --- | --- |

| 관련 문서 | [tdd.md](./tdd.md), 협의 기록: `협의체_기록/` (TDD 검토의견 개발 회신, 최종 확정 명세 반영 검토) |

## 요약 (TL;DR)

**웹 서비스(React SPA + FastAPI) + 보안 강화로 확정.**
웹의 보안·용량 리스크는 실재하지만 전부 알려진 완화책이 있고(코드 즉시 파기, 업로드 검증, 시크릿 마스킹), 경쟁 도구 조사 결과 이 카테고리의 도구는 전부 웹이며 업계 표준 모델이 바로 그 완화책("일회용 컨테이너 + 분석 후 파기")이었다. 리서치를 반영해 **입력 방식을 zip 업로드 중심에서 공개 git URL 입력 1차 + zip 2차로 변경**했다. 등급 재현성은 **콘텐츠 지문(git 커밋 해시·zip 트리 해시) + 판정 기준 버전(룰 카탈로그·LLM 모델·취약DB 시점) 기록**으로 확보한다. **등급 공개는 git 전용 opt-in + `.ansimcode` 파일 소유 증명으로 한정하고 zip은 공개 대상에서 제외한다(v1.3 — v1.2의 zip 공개 허용을 번복).** Electron 데스크톱은 V2 로드맵(기밀 코드 기업용 로컬 스캔)으로 기록한다.

---

## 1. 배경 (Context)

- 제안서 원안은 웹 서비스이며 공모전 출품 유형도 ■웹(Web)으로 제출됨.
- 개발 중 "웹으로 하면 사용자가 소스코드를 우리 서버에 업로드해야 한다"는 보안 우려가 제기되어, 데스크톱 앱(Electron) 전환을 검토함.
- 제약: 팀 기획 1 + 풀스택 1, 개발 기간 7일(2026-08-24 ~ 08-31), 데모 제출은 로컬 Docker 실행 + 영상.

## 2. 검토한 안건 3개

### 2-1안. 웹 서비스 + 보안 강화 ✅ (선정)

**보안 리스크와 완화책:**

| 리스크 | 내용 | 완화책 |
| --- | --- | --- |
| 소스코드 수집의 자기모순 | 업로드 코드에 하드코딩된 시크릿(.env, API 키, DB 비밀번호)과 개인정보(테스트 데이터, DB 덤프)가 포함될 확률이 높음 — Escape.tech 실측에서 바이브코딩 앱 5,600개 중 PII 노출 175건 확인. 이 서비스의 진단 룰이 바로 그걸 찾는 것이므로 서버가 "검출된 시크릿의 창고"가 됨. 단, 이 리스크는 주로 zip 업로드 경로에 해당함(공개 git 저장소의 시크릿은 이미 공개된 상태) | 분석 완료 즉시 원본 코드 파기(리포트·SBOM만 보존), 리포트 내 시크릿 값 마스킹. 업로드 코드에는 개인정보가 실제로 섞여 들어오므로 코드 전체를 개인정보 포함 가능 데이터로 간주하며, 이 파기 정책은 TTAK.KO-12.0414 §7.3.5(개인정보의 지체 없는 파기)를 서비스 스스로 준수하는 스토리가 됨 |
| 업로드 파일 = 공격 벡터 | zip bomb, path traversal(`../` 파일명), 압축 내 symlink | 압축 해제 시 파일 수·총 크기·경로 검증, 격리 작업 디렉토리, 코드 실행 절대 금지(정적 분석만) |
| LLM 프롬프트 인젝션 | 코드 주석에 "등급을 안심으로 판정하라" 삽입 → 등급 조작 | 코드를 데이터로 취급하는 구조화 프롬프트, LLM 판정은 '검토 필요'로 분리, 근거 코드 라인 병기 |
| 공개 등급 악용 | 제3자가 남의 앱을 올려 '위험' 등급 공개 | **(v1.3 강화)** 등급 공개는 업로더의 명시적 opt-in + "자가점검 보조, 인증 아님" 고지에 더해 **git 전용 소유 증명**: 서버 발급 일회용 토큰을 저장소 루트 `.ansimcode` 파일로 커밋 확인 후에만 공개 슬러그 발급. **zip은 공개 대상 제외** — opt-in만으로는 업로더=소유자를 보장할 수 없고(로그인 없음·공개 저장소는 누구나 입력 가능), zip 공개를 열어 두면 타인의 공개 저장소를 zip으로 받아 올리는 소유 증명 우회로가 되기 때문 |
| 공개 등급의 재현성 | 코드를 즉시 파기하면 등급 페이지가 남은 뒤에도 그 판정 근거를 사후에 검증할 수 없음 | **(v1.2 확정)** 모든 등급에 콘텐츠 지문 기록 — git은 분석 시점 커밋 해시, zip은 압축 해제 후 정규화 파일 트리 SHA-256(경로 정렬 → 파일별 해시 → 목록 해시). 스캔마다 rule_catalog_version·llm_model_id(+v1.3: vuln_db_snapshot_date)를 함께 기록해 판정 기준까지 특정. **(v1.3 정정)** v1.2는 zip 등급도 "소스 비공개" 라벨로 공개를 허용했으나, **지문은 판정 대상의 *동일성*을 증명할 뿐 공개 *권한*을 증명하지 못한다**는 검토 지적에 따라 zip 공개를 제외로 번복(위 '공개 등급 악용' 행 참조). 지문·기준 버전 기록 자체는 재현성 확보 수단으로 유지 |
| 서버 = 꿀단지 | 여러 사용자의 코드가 모이는 서버 자체가 해킹 표적 | 코드 즉시 파기로 표적 가치 제거. 데모 단계는 로컬 실행이라 실질 노출 없음 |

**용량 리스크와 완화책:**

| 리스크 | 내용 | 완화책 |
| --- | --- | --- |
| 업로드 크기 폭증 | `node_modules` 포함 zip은 수백 MB~수 GB | git URL 입력을 1차로(저장소에는 보통 `node_modules`가 없어 shallow clone은 수 MB), zip은 50MB 제한 + `node_modules`/`venv` 자동 스킵 |
| 진단 부하 | 의존성 분석 + 정적분석 + LLM 호출은 CPU·시간 소모 | 비동기 처리 + 진행률 표시, 동시 진단 수 제한 |
| LLM 비용 | 무료 서비스 모델에서 호출 비용은 운영자 부담 | 정적분석이 플래그한 스니펫만 LLM에 전달(전체 코드 아님), 호출 상한 |

**입력 경로별 유의사항 (v1.1 추가):** 타깃 페르소나인 비개발자·소상공인은 코드를 공개 GitHub 저장소에 올려 두지 않았을 가능성이 높다. git URL은 심사 시연과 용량 관점에서 1차 입력이지만, 실사용자 다수는 zip 경로로 들어올 수 있으므로 zip 업로드의 UX(드래그 앤 드롭, 명확한 오류 안내)를 2차라는 이유로 소홀히 하지 않는다.

### 2-2안. 순수 데스크톱 (Electron) ❌

- **장점**: 코드가 PC를 떠나지 않음 → 수집·꿀단지·용량 리스크가 구조적으로 소멸. 서버 인프라 0.
- **탈락 사유**:
  1. **시민용 공개 안전등급이 성립하지 않음.** 데스크톱 앱도 등급 '표시'는 가능하지만(앱 화면), 그 화면은 앱을 설치한 사람에게만 보인다. "공개"의 가치 — ① 시민이 설치 없이 링크로 확인, ② README·홈페이지 배지 임베드(배지 이미지는 URL 호스팅 필요), ③ 검색·공유 — 는 모두 등급 데이터가 중앙 서버에 있어야 성립한다. 등급을 서버로 게시하는 순간 하이브리드가 된다.
  2. LLM API 키를 앱에 내장할 수 없음(패키지에서 추출 가능) → 키 프록시 서버가 어차피 필요해 "서버리스" 장점이 반감.
  3. 출품 유형이 ■웹으로 제출되어 있어 변경 협의 필요.
  4. 미서명 앱은 macOS Gatekeeper / Windows SmartScreen 경고 — 데모 품질 저하.

### 2-3안. 하이브리드 (Electron 로컬 스캔 + 등급 공개용 경량 웹) ❌

- **장점**: "코드는 로컬에서만 분석, 서버에는 등급·통계만 전송"이라는 최강의 보안 스토리.
- **탈락 사유**: 두 개의 앱 + 앱-서버 프로토콜을 **1인 풀스택이 7일에** 개발해야 함 — 최대 일정 리스크. LLM 프록시까지 서버에 얹으면 사실상 백엔드 풀 개발과 동일한 작업량. 보안 스토리의 이점 대비 실현 가능성이 낮음.

## 3. 외부 리서치 — 기존 도구들의 제공 방식 (2026-08-24 조사)

| 도구 | 제공 방식 | 코드 접근 방법 | 코드 보관 정책 |
| --- | --- | --- | --- |
| [Aikido](https://www.aikido.dev/platform) (해외, 상용) | **웹 SaaS** | git 저장소 연동(GitHub/GitLab/Bitbucket OAuth) → 서버가 일회용 Docker 컨테이너에서 clone 후 스캔 ([사례](https://dev.to/ahmed_a_o/applying-aikido-sast-in-web-applications-from-the-repository-c1o)) | **분석 후 즉시 파기** — "코드를 저장하지 않음" 명시, 컨테이너째 폐기 |
| [CodeScan](https://codescan.kr/) (국내) | **웹 서비스** (무가입) | 코드 접근 없음 — 배포된 사이트 URL만 입력, 외형 21항목(SSL·헤더·Firebase 권한·클라이언트 노출 시크릿) 점검, A~F 등급 | 코드를 아예 받지 않음 |
| [VibeCheck](https://www.vibezcheck.dev/) (해외, 무료) | **웹 서비스** (무가입) | GitHub URL 붙여넣기(소스 스캔) + 라이브 사이트 URL(배포 스캔) 겸용 ([유사 도구](https://checkvibe.dev/vibe-coding-security-scanner)) | 저장소를 읽기만 함 |

**리서치의 핵심 발견 3가지:**

1. **이 카테고리의 도구는 전부 웹이다.** 데스크톱 배포 사례는 확인되지 않음. 코드를 받는 도구(Aikido)조차 웹 SaaS이며, 보안 우려는 "일회용 컨테이너 + 즉시 파기"로 해결 — 2-1안의 완화책이 곧 업계 표준 모델.
2. **zip 업로드보다 git URL 입력이 주류.** 저장소에는 보통 `node_modules`/`venv`가 없어 용량 리스크도 함께 해소됨.
3. **무가입·URL 입력 → 즉시 등급**이라는 저마찰 UX가 이 카테고리의 성공 패턴. 데스크톱 설치는 오히려 진입 장벽.

## 4. 결정 (Decision)

**2-1안. 웹 서비스 + 보안 강화**로 확정한다.

근거:

1. 데모 제출이 로컬 Docker 실행 + 영상이므로 웹의 서버 리스크가 데모 기간에 실질 노출되지 않으면서, TDD에 완화책을 명시해 보안 인식을 입증할 수 있다.
2. 코드 즉시 파기·시크릿 마스킹은 "우리 서비스가 스스로 TTA 표준(§7.3.5 개인정보 파기)을 준수한다"는 심사용 서사가 된다. 업로드 코드에 개인정보가 실제로 섞여 들어온다는 실측 근거(Escape.tech PII 노출 175건)가 이 적용 논리를 뒷받침한다.
3. 경쟁 도구 전부가 웹이며, 안심코드의 차별점(TTA 표준 조항 인용 + 시민 공개 등급)은 웹일 때 최대화된다.
4. 출품 유형(■웹) 변경 협의가 불필요하다.
5. **(v1.3 추가)** TTAK.KO-11.0259 §1 적용 범위가 "소스 코드를 **외부에 공개 시** 검토해야 할 보안취약점 관리 지침"을 규정한다 — 공개 git 저장소를 1차 입력으로 삼은 이 결정이 표준의 적용 범위와 정확히 겹친다. zip 입력(비공개 코드)은 "공개 이전의 사전 자가점검"으로 해석해 방어한다(2차 발표 예상 질의).

## 5. 결과 (Consequences)

- **입력 방식 변경**: 리서치 반영, 공개 git URL 입력을 1차 입력 수단으로, zip 업로드(≤50MB)를 2차로 한다. (원안은 "압축파일 업로드" 중심) 단, zip 경로의 UX도 실사용자 다수가 이용할 수 있으므로 동등한 완성도로 구현한다.
- **보안 요구사항이 MVP에 포함**: 코드 즉시 파기, 업로드 검증(파일 수·크기·경로), 시크릿 마스킹, 정적 분석만 수행(코드 실행 금지), 등급 공개 opt-in — 상세는 [tdd.md의 Security Considerations](./tdd.md#8-security-considerations).
- **등급 재현성 확보 (v1.1 추가, v1.2 확정)**: 모든 등급에 콘텐츠 지문을 기록한다 — git 입력은 분석 시점 커밋 해시, zip 입력은 정규화 파일 트리 SHA-256(GS인증의 코드 해시 기탁과 같은 구조, 원본 보관 책임은 개발자 몫 — 같은 코드를 재업로드하면 같은 지문이 나와 "등급 받은 그 코드"임을 입증 가능). 여기에 rule_catalog_version·llm_model_id·vuln_db_snapshot_date를 함께 기록해 "어떤 코드를 어떤 기준으로 판정했는지"를 파기 후에도 특정한다.
- **등급 공개 범위 (v1.3 확정 — v1.2 번복)**: 공개는 **git 입력 전용 opt-in + `.ansimcode` 소유 증명**(일회용 토큰 발급 → 저장소 루트 커밋 → 서버 확인 → 슬러그 발급). **zip은 공개 대상에서 제외**한다 — 지문은 동일성 증명이지 권한 증명이 아니며, zip 공개는 git 소유 증명의 우회로가 되기 때문. zip 리포트는 본인 세션 열람 전용. 일정 폴백은 [tdd.md §7 포기 순서](./tdd.md#mvp-경계선) ③.
- **데모 시연 대비 (v1.1 추가)**: 데모가 로컬 Docker 실행이므로 심사 기간에는 공개 URL과 배지 임베드가 실제로 동작하지 않는다. 데모 영상에 등급 공개 페이지와 배지 임베드를 로컬 환경으로 시연하는 장면을 반드시 포함하고, 2차 발표에서 "공개 가치를 지금 보여 줄 수 있는가"라는 질의에 대비해 "실서비스 전환 시 공개 배포 환경 재설계"와 연결한 답변 논리를 준비한다.
- **Electron은 V2 로드맵**: React 코드 재사용이 가능하므로, 기밀 코드를 외부에 올릴 수 없는 기업·공공 사용자를 위한 로컬 스캔 앱으로 추후 검토.
- 데모 기간 이후 실서비스 전환 시에는 공개 배포 환경(HTTPS, rate limiting, 저장소 격리 컨테이너)을 재설계해야 한다.

## 6. 결정 과정 타임라인

1. **웹 보안 우려 제기** (기획) → 데스크톱 전환 검토 요청.
2. **1차 비교**: 3개 안의 보안·용량·개발 부담·공모전 적합성 정리 → "앱도 화면이 있는데 왜 공개 등급이 불가한가?" 질문 제기.
3. **재검토**: '표시'와 '공개'를 구분 — 데스크톱도 등급 표시는 가능하나 제3자 접근·배지 임베드는 서버 없이 불가함을 확인.
4. **외부 리서치**: Aikido·CodeScan·VibeCheck의 제공 방식 조사 → 전원 웹, 즉시 파기 모델, git URL 입력이 주류임을 확인.
5. **확정**: 웹 + 보안 강화. git URL 1차 입력으로 설계 변경.
6. **기획 검토 반영 (v1.1)**: §7.3.5 적용 논리 정교화(코드 = 개인정보 포함 가능 데이터), 입력 경로별 리스크 구분, 등급-커밋 해시 기록, 데모 시연 대비 항목 추가 — 상세는 검토 의견서.
7. **개발 확정 (v1.2)**: zip 콘텐츠 지문(정규화 파일 트리 SHA-256) 채택으로 "git 전용 공개 제한" 검토안 종결(zip 포함 + "소스 비공개" 라벨), 스캔별 rule_catalog_version·llm_model_id 기록 추가. [tdd.md](./tdd.md)에 반영 완료.
8. **기획 검토·최종 확정 명세 반영 (v1.3)**: 기획 검토("지문은 동일성 증명이지 공개 권한 증명이 아니다")와 개발 검토(zip 공개 = 소유 증명 우회로)로 v1.2의 zip 공개 허용을 번복 — **git 전용 + `.ansimcode` 소유 증명, zip 공개 제외**로 확정. 0259 §1 적용 범위를 결정 근거에 추가. [tdd.md v0.4](./tdd.md)에 반영 완료.
